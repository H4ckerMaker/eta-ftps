# Encrypted Traffic Analysis
## Short Description of the Project/ Documentation of the Project
 
The goal of this project is to investigate **encrypted network traffic classification into four traffic categories** by comparing two machine learning approaches: Random Forest and ODENet-LSTM.

The study uses Random Forest as a traditional machine learning baseline and ODENet-LSTM as a sequence-based deep learning approach inspired by Roy et al., Fast and lean encrypted Internet traffic classification (Computer Communications, 186, 2022, pp. 166–173).

The comparison aims not only to evaluate classification performance but also to investigate the factors that influence accuracy and the limitations of traffic classification based on encrypted packet metadata.
 
 The categories we used are as follows:

| Category | Examples |
|----------|----------|
| Streaming | Video and audio streaming |
| Web browsing | Regular page browsing |
| File transfer | File uploads and downloads (e.g. scp, ftps)|
| Messaging | Chat applications (e.g. WhatsApp, Telegram, Discord) |
 
Application payloads are **never decrypted**. Classification relies only on metadata that is visible to an observer on the network.
 
## Preliminary observations

### 1. Initial Scope: File Identification over FTPS

Given a pool of files hosted on an FTPS server, can an eavesdropper identify which one is being downloaded by looking only at encrypted traffic metadata?

To test this, we deployed an FTPS server on **Microsoft Azure**, uploaded **5 files of different sizes**, and captured the traffic generated by downloading each of them.


Following the methodology of *Fast and Lean Encrypted Internet Traffic Classification* (Roy, Shapira, Shavitt, 2022), we extracted two features from each packet capture:

- **Packet size**
- **Inter-arrival time** (IAT), i.e. the time between consecutive packets

Rather than reproducing the paper's architecture, we deliberately opted for a **simpler model** to evaluate whether a lightweight approach could still reach a reasonable accuracy, even if lower than the published results. To do so, we **aggregated** both features for each capture file.

### 2. Findings and Limitations of IAT and Size aggregated features

The analysis revealed an important limitation of the initial scope:

- **Packet size** (aggregated) was clearly **different across files**, making it a discriminative feature.
- **Inter-arrival time** was **virtually identical across all files**, so it contributed no useful information. This happens because FTPS transfers data at a roughly constant rate, regardless of the file being downloaded.

As a result, the classifier could only rely on size-based information, which defeats the purpose of combining both features.

Given these results, we **shifted the focus of the project**: instead of distinguishing different contents within the same protocol, we now classify the **type of traffic flow across different protocols**, where both size and timing patterns are expected to be more informative.

To address this limitation, we drew inspiration from previous work project on encrypted traffic classification, which relies on a much richer set of flow-level features.

### 2. Feature extraction: parsing

We built a parser that splits each capture file into individual flows and extracts a set of aggregated features for each one. Initially, we extracted the following three features:

1. `packet_count`: total number of packets in the flow
2. `total_bytes`: total number of bytes transferred in the flow
3. `duration`: time elapsed between the first and the last packet of the flow

### 3. Baseline: Random Forest

As a simple baseline, we trained a Random Forest classifier to distinguish the four traffic categories.

- **Training:** each capture is split into flows, and every flow is represented by its three features. The model is trained on these flow-level samples, using the category of the capture as the label.
- **Validation:** for each capture, the model classifies every flow individually. The capture is then assigned to the category that receives the most votes (**majority voting**).

#### 3.1. Limitations: Overfitting

When evaluated on a held-out split of our own dataset, the model reached a high accuracy (**TODO**). However, when tested on new captures from real sessions recorded independently, the accuracy dropped drastically (**TODO**). This indicates that the model was **overfitting** the training set.

We realised that the three initial features do not describe the *behaviour of the protocol*, but only the **volume of data** and the **length of the session**. As a result, the classifier can be easily misled: a 40-second session of one category may look very similar to a 40-second session of another, while two sessions of the same category with different durations (e.g. 2 s and 40 s) may be assigned to different classes.

#### 3.2. Improved Feature Set

To address this, we extended the feature set with additional aggregated features that describe the packet size distribution and the traffic rhythm, rather than its overall volume:

4. `mean_packet_size`: average packet size
5. `min_packet_size`: smallest packet size
6. `max_packet_size`: largest packet size
7. `min_interarrival_time`: shortest gap between consecutive packets
8. `max_interarrival_time`: longest gap between consecutive packets
9. `mean_interarrival_time`: average gap between consecutive packets
10. `bytes_per_sec`: average throughput in bytes per second
11. `packets_per_sec`: average packet rate

We chose these features because they are largely **independent of the session's duration and total size**. With this richer feature set, the model also performed well on the external real-world captures (**TODO: accuracy**).
 
### 4. Limitations of the baseline

We then tried to make the evaluation more realistic. So far, each external capture was given to the model as a **complete session**. A real attacker, however, has no such guarantee: the capture may start in the middle of a session (after some packets have already been exchanged) or end before the session is closed.

To test this scenario, we fed the Random Forest classifier **truncated captures** of incomplete sessions for each category. The results were poor, with a very low accuracy (**TODO**).

This happens because aggregated features are a poor representation of real-time traffic. They summarise the flow as a whole, so they implicitly assume that the **entire session** is available:

- **They depend on the observation window.** Statistics such as `mean_packet_size` or `max_interarrival_time` change when the beginning or the end of the session is missing, so a truncated capture produces feature values that the model never saw during training.
- **They lose temporal information.** Aggregation discards the order of the packets and the evolution of the traffic over time (bursts, pauses, periodic patterns), which are exactly the characteristics that distinguish one protocol from another.
- **They rely on distinctive phases of the session.** Connection setup and teardown are often highly informative, but a partial capture may not include them.

For this reason, we decided to move to a model that can represent real-time traffic well, one that works directly on the **sequence of packets** rather than on session-level summaries, and can therefore classify a flow even from a partial observation.

### 5. A better-suited model? ODE-LSTM
 
After reviewing the literature (including reports available through the KTH Library), we adopted the approach proposed by Roy, Shapira and Shavitt in *"Fast and lean encrypted Internet traffic classification"* (Computer Communications, 2022).
 
Instead of aggregated statistics, this method uses only **two per-packet features**:
 
- packet size
- inter-arrival time

These are fed as a time series to a **Neural ODE combined with an LSTM**. The ODE uses the inter-arrival times to model how the hidden state of the flow evolves between packets, which makes the model well suited to irregularly spaced events such as network traffic. 

The model performed well also on the **external real-world truncated captures** of incomplete sessions (acc: 0.9)

### Known difficulties and observations

While deciding which features to extract for our Random Forest classifier, we inspected the `.pcap` captures in detail and noticed two issues in our dataset.

#### 1. Heterogeneous behaviour within the CHAT category

The CHAT category includes three web apps: **Discord**, **WhatsApp** and **Telegram**. Their traffic patterns differ:

- **Discord and WhatsApp** are *event-driven*: the server sends packets to the client only when a new message is received, and the client sends packets only when a message is sent.
- **Telegram** exchanges packets *continuously*, even when no message is sent or received, which looks like a keep-alive (heartbeat) mechanism. Sending or receiving a message only produces packets of a larger size.

For Telegram, the inter-arrival time is therefore not informative, and only packet size carries a useful signal. This heterogeneity is the likely reason why CHAT is the category with the slightly lower accuracy.

#### 2. Merging AUDIO into STREAMING

The project initially had **five categories**, including a separate AUDIO class. With five classes, the model frequently confused AUDIO and STREAMING. Both categories consist of a server sending a continuous, one-directional flow of media data to the client, typically in regularly spaced chunks, so their size and timing patterns are very similar and hard to separate with our features.

Since audio can be considered a particular case of streaming, we decided to **merge AUDIO into STREAMING**, ending up with four categories.

## ODENet: build, train and test

### Requirements

- Python **3.11 – 3.13**. Very recent Python releases may not have PyTorch wheels yet; in that case `pip` fails with `No matching distribution found for torch`.
- `requirements.txt` must include `torch`, `numpy` and `scapy` (scapy is used to read PCAP files).

### Dataset layout

Put the captures in one folder per class:

```
dataset/
├── BROWSING/        *.pcap
├── CHAT/            *.pcap
├── FILE_TRANSFER/   *.pcap
└── STREAMING/       *.pcap
```

The folder name is the class label.

### 1. Set up the environment

```bash
cd ODENet
python3 -m venv .venv
.venv/bin/python3 -m pip install -r requirements.txt
```

### 2. Convert the PCAP files to CSV

```bash
.venv/bin/python3 pcap_to_csv.py dataset/CHAT --name my_chat
.venv/bin/python3 pcap_to_csv.py dataset/STREAMING --name my_streaming
.venv/bin/python3 pcap_to_csv.py dataset/BROWSING --name my_browsing
.venv/bin/python3 pcap_to_csv.py dataset/FILE_TRANSFER --name my_filetransfer
```

Each CSV row is one unidirectional flow (5-tuple). The files are written to `classes_csvs/<class>/reg/<name>.raw.csv`.

- Flows shorter than 20 packets are discarded (`--min-packets`).
- An existing CSV is not overwritten unless you pass `--force`.

### 3. Train the model

```bash
.venv/bin/python3 train.py
```

`train.py` loads every `classes_csvs/*/reg/my_*.raw.csv`, splits the flows 80/20 (train/test), balances the training set and trains for 100 epochs. At the end it prints the macro-F1 and the confusion matrix.

The best checkpoint is saved as `best_<model>_n<n>.pt` (e.g. `best_ode_n20.pt` for the default ODE-LSTM). The model is selected with `model_name` in `main()`: `ode`, `lstm_size` or `lstm_both`.

The class order is alphabetical and is printed at the start of training (`classes: {...}`). You need it in the next step.

### 4. Classify an external capture

```bash
.venv/bin/python3 predict.py capture.pcap --ckpt best_ode_n20.pt --classes BROWSING,CHAT,FILE_TRANSFER,STREAMING
```

The script prints the longest flows with their predicted class and confidence, and a summary with the share of traffic per class.

- `--classes` must follow the training order. It can be omitted if the checkpoint already stores the class names.
- `--n` must match the value used in training (default 20).
- A `.csv` file in the same format as the training CSVs is also accepted as input.

> **Note:** a capture must be converted the same way as the training data (same packet-size definition and protocols), otherwise the predictions degrade. The model always picks one of its own classes, so unrelated traffic (DNS, telemetry) is also assigned a class.
