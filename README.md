# Encrypted Traffic Analysis
## Short Description of the Project/ Documentation of the Project
 
The goal of this project is to investigate **encrypted network traffic classification into four traffic categories** by comparing two machine learning approaches: Random Forest and ODENet-LSTM.

The study uses Random Forest as a traditional machine learning baseline and ODENet-LSTM as a sequence-based deep learning approach inspired by Roy et al., Fast and lean encrypted Internet traffic classification (Computer Communications, 186, 2022, pp. 166–173).

The comparison aims not only to evaluate classification performance but also to investigate the factors that influence accuracy and the limitations of traffic classification based on encrypted packet metadata.
 
 The categories we used are as follows:

| Category | Examples |
|----------|----------|
| Streaming | Video and audio streaming |
| Web browsing | Regular page browsing |
| File transfer | File uploads and downloads (e.g. scp, ftps)|
| Messaging | Chat applications (e.g. WhatsApp, Telegram, Discord) |
 
Application payloads are **never decrypted**. Classification relies only on metadata that is visible to an observer on the network.
 
## Preliminary observations

### 1. Initial Scope: File Identification over FTPS

Given a pool of files hosted on an FTPS server, can an eavesdropper identify which one is being downloaded by looking only at encrypted traffic metadata?

To test this, we deployed an FTPS server on Microsoft Azure, uploaded 5 files of different sizes, and captured the traffic generated by downloading each of them.


Following the methodology of *Fast and Lean Encrypted Internet Traffic Classification* (Roy, Shapira, Shavitt, 2022), we extracted two features from each packet capture:

- **Packet size**
- **Inter-arrival time** (IAT), i.e. the time between consecutive packets

Rather than reproducing the paper's architecture, we deliberately opted for a simpler model to evaluate whether a such an approach could still reach a reasonable accuracy, even if lower than the published results. To do so, we aggregated both features for each flow in the capture file.

### 2. Findings and Limitations of IAT and Size aggregated features

The analysis revealed an important limitation of the initial scope:

- **Packet size** (aggregated) was clearly different across files, making it an obvious feature to distinguish. Using this, it was somewhat trivial to determine the corresponding file.
- **Inter-arrival time** was virtually identical across all files, so it contributed no useful information. This happens because FTPS transfers data at a roughly constant rate, regardless of the file being downloaded.

As a result, our classifier could only rely on size-based information, which defeats the purpose of combining both features. Additionally, this would prove problematic if trying to determine which of two same-sized files was downloaded.

Given these results, we pivoted to a different topic within the area of network traffic analysis. Instead of distinguishing different contents within the same protocol, we now classify the type of traffic flow across different protocols, where we expected both size and timing patterns to be more informative.

To determine, which features to use, we drew inspiration from previous work project on encrypted traffic classification.

## Methodology
 
### 1. Data collection
 
For each category we captured repeated experiments and saved the traffic as `.pcap` or `pcapng` files.
 
For the **streaming** class, we recorded some audio clips, then uploaded them to our server and split them into random sized audio snippets. We then listened to the audio snippets on our computer whilst using tcpdump on the server to record the traffic. Additionally, for the video streaming we configured an Nginx server to host video files using HTTP Live Streaming (HLS). The videos were divided into segments and made accessible through .m3u8 playlists. The server used HTTPS on port 443, with a self-signed TLS certificate to encrypt communication. For each video file, we captured the traffic on port 443 and requested the video from the server. Lastly, we manually recorded some sessions for youtube video streaming and netflix movie streaming.

For the **file transfer** class, we used a script to create and upload/download random sized files to our server using different protocols such as scp and ftps.

For the **messaging** class, we used tcpdump to record different sessions of chatting using chat web apps such as: discord, whatsapp and telegram.

For the **web browsing**, we used tcpdump to record different sessions of browsing the internet and visiting websites.

### 2. Feature extraction: parsing

We built a parser that splits each capture file into individual flows and extracts a set of aggregated features for each one. Initially, we extracted the following three features:

1. `packet_count`: total number of packets in the flow
2. `total_bytes`: total number of bytes transferred in the flow
3. `duration`: time elapsed between the first and the last packet of the flow

### 3. Baseline: Random Forest

As a simple baseline, we trained a Random Forest classifier to distinguish the four traffic categories.

- Training: each capture is split into flows, and every flow is represented by its three features. The model is trained on these flow-level samples, using the category of the capture as the label.
- Validation: for each capture, the model classifies every flow individually. When evaluating the whole capture, the capture is assigned to the category that receives the most votes (majority voting). This approach of course has its limitations, which we will explain further.

#### 3.1. Limitations: Overfitting

When evaluated the model on a portion of our own dataset, the model reached a high accuracy (**0.9807**). However, when tested on new captures from real sessions recorded independently, the accuracy dropped drastically (**0.5322**). This indicates that the model was **overfitting** the training set.

We realised that the three initial features do not describe the *behaviour of the protocol*, but only the **volume of data** and the **length of the session**. As a result, the classifier can be easily misled: a 40-second session of one category may look very similar to a 40-second session of another, while two sessions of the same category with different durations (e.g. 2 s and 40 s) may be assigned to different classes.

#### 3.2. Improved Feature Set

To address this, we extended the feature set with additional aggregated features that describe the packet size distribution and the traffic rhythm, in addition to its overall volume:

1. `packet_count`: total number of packets in the flow
2. `total_bytes`: total number of bytes transferred in the flow
3. `flow_duration`: time elapsed between the first and the last packet of the flow
4. `forward_packet_count`: number of packets in the forward direction (the side that opened the connection)
5. `backward_packet_count`: number of packets in the backward direction
6. `forward_bytes`: total bytes in the forward direction
7. `backward_bytes`: total bytes in the backward direction
8. `forward_mean_packet_size`: average packet size in the forward direction
9. `backward_mean_packet_size`: average packet size in the backward direction
10. `mean_packet_length`: average packet size over the whole flow
11. `std_packet_length`: standard deviation of the packet size
12. `mean_iat`: average gap between consecutive packets
13. `std_iat`: standard deviation of the gaps between consecutive packets
14. `min_iat`: shortest gap between consecutive packets
15. `max_iat`: longest gap between consecutive packets
16. `burst_count`: number of bursts in the flow (a burst is a group of packets separated by a silence gap larger than 1 s)
17. `mean_burst_bytes`: average number of bytes per burst
18. `max_burst_bytes`: bytes in the largest burst
19. `mean_idle_time`: average length of the silence gaps between bursts


We chose these features because they describe additional properties of the protocol, instead of just the traffic volume. With this richer feature set, the model also performed well on the external real-world captures. It accurately classified newly captured traffic for streaming, browsing, chatting and file transfer. Only classifying streaming suffered from a lower accuracy, due to programs like youtube containing elements, that resemble browsing too.
 
### 4. Limitations of the baseline

We then tried to make the evaluation more realistic. So far, each external capture was given to the model as a complete session. A real attacker, however, has no such guarantee: the capture may start in the middle of a session (after some packets have already been exchanged) or end before the session is closed.

To test this scenario, we fed the Random Forest classifier short captures of truncated sessions for each category. The results were poor, with a very low accuracy of about 40%.

Because the model relies on flow-wide statistical summaries, including forward and backward packets, it depends on seeing complete connection captures.
Because the connection was not established during the traffic capture, the script cannot reliably determine the sender and the receiver for example.

This happens because aggregated features are an unrealistic representation of real-time traffic. They summarise the flow as a whole, so they implicitly assume that the entire session is available. Statistics such as `mean_packet_size` or `max_interarrival_time` change when the beginning or the end of the session is missing, so a truncated capture produces feature values that the model never saw during training. For example a short capture, that only happens to record streaming activity in between two bursts may look like a chat capture. Aggregation also discards the order of the packets and the evolution of the traffic over time (bursts, pauses, periodic patterns), which are exactly the characteristics that distinguish one protocol from another.
In addition to that, the connection setup and teardown are crucial to determine which party is the client and which is the server, but a partial capture may not include them.

For this reason, we decided to move to a model that can represent real-time traffic well, one that works directly on the sequence of packets rather than on session-level summaries, and can therefore classify a flow even from a partial observation.

### 5. A better-suited model? ODE-LSTM
 
After reviewing the literature (including reports available through the KTH Library), we adopted the approach proposed by Roy, Shapira and Shavitt in *"Fast and lean encrypted Internet traffic classification"* (Computer Communications, 2022).
 
Instead of aggregated statistics, this method uses only **two per-packet features**:
 
- packet size
- inter-arrival time

These are fed as a time series to a Neural ODE combined with an LSTM. The ODE uses the inter-arrival times to model how the hidden state of the flow evolves between packets, which makes the model well suited to irregular events such as network traffic. 

The model performed well also on the external real-world truncated captures of incomplete sessions (acc: 0.9)
 
Since this model is a very advanced mathematical model, it would have been a substantial engineering effort to implement it from scratch and would have not been realistic within the projects allocated time frame. To be able to evaluate our implementation in spite of that, we chose to use develop it using AI-assistance and adjust the generated model to fit our provided dataset.

### 6. Comparison

Both models were trained and evaluated on the same data and compared on previously unseen traces.

| Model | Input | Full sessions (accuracy) | Partial captures (accuracy) |
|---|---|---|---|
| Random Forest | 19 aggregated flow features | 0.98 | 0.40 |
| ODE-LSTM | Packet sequence (size, inter-arrival time) | N/A | 0.9088 |

**Evaluation setup.** The test set consists of real captures recorded independently from the training data. We evaluated Random Forest in two scenarios:

- **Full sessions:** each capture contains the entire session from the start.
- **Partial captures:** each capture is truncated, simulating an attacker who starts or stops sniffing at an arbitrary point of the session.

and ODE-LSTM on just one scenario:

- **Partial captures**

## Results

On complete sessions, the Random Forest achieved a very high accuracy of 98% when using 19 features. Introducing Burst-sizes as a feature proved to be critically important, because it increased classification accuracy on previously unseen files substantially. As detailed previously, the accuracy dropped significantly, when providing truncated captures, depending on the files and the truncated parts. The ODE-LSTM in turn proved to be very accurate while only requiring very few packets.

Overall, these results suggest that sequence-based models are better suited to realistic, real-time traffic analysis, while aggregated features are sufficient only when the full session is available.
 
### Known difficulties and observations

While deciding which features to extract for our Random Forest classifier, we inspected the `.pcap` captures in detail and noticed two issues in our dataset.

#### 1. Heterogeneous behaviour within the CHAT category

The CHAT category includes three web apps: **Discord**, **WhatsApp** and **Telegram**. Their traffic patterns differ:

- **Discord and WhatsApp** are *event-driven*: the server sends packets to the client only when a new message is received, and the client sends packets only when a message is sent.
- **Telegram** exchanges packets *continuously*, even when no message is sent or received, which looks like a keep-alive mechanism. Sending or receiving a message only produces packets of a larger size.

For Telegram, the inter-arrival time is therefore not informative, and only packet size carries a useful signal. This heterogeneity is the likely reason why CHAT is the category with the slightly lower accuracy.

#### 2. Merging AUDIO into STREAMING

The project initially had **five categories**, including a separate AUDIO class. With five classes, the model frequently confused AUDIO and STREAMING. Both categories consist of a server sending a continuous, one-directional flow of media data to the client, typically in regularly spaced chunks, so their size and timing patterns are very similar and hard to separate with our features.

Since audio can be considered a particular case of streaming, we decided to merge AUDIO into STREAMING, ending up with four categories.

#### 3. Splitting Files based on filenames instead of flows

Initially, we trained the Random Forest using a regular 80/20 split on the extracted flows. Though we realized later on, that this may lead to the model being trained on 80% of flows of one file and validated on 20% of the same file. We fixed this, using a `GroupShuffleSplit`, splitting the files instead of the flows in 80/20.
 
## How to Run the Code/ Documentation of Testing the Project

### Build and test the Random Forest Classification model

## Requirements
 
- Python 3.11 – 3.13
- Dependencies: `scikit-learn`, `pandas`, `scapy`, `joblib`
## Dataset Layout
 
Place your capture files anywhere inside the `dataset/` directory of /ODENet. Since both the ODENet and the random forest are trained on the same data set, this avoids uploading the large traffic capture files twice. The class label is taken from a keyword in the **file name**:
 
| Keyword in file name | Label |
|---|---|
| `browse` | BROWSING |
| `chat` | CHAT |
| `file` | FILE TRANSFER |
| `streaming` | STREAMING |
 
Example:
 
```text
dataset/
├── browse_001.pcapng
├── chat_001.pcapng
├── file_transfer_ftps_001.pcapng
└── streaming_001.pcapng
```
## 1. Set up the Environment
 
Create a virtual environment and install the dependencies:
 
```bash
cd RandomForest
python -m venv .venv
.venv/bin/python3 -m pip install -r requirements.txt
```

## Training the Model

Ensure the `dataset_dir` path in line 17 in `random_forest_classifier.py` points correctly to the `dataset/` folder. Then run the training script:

```bash
python random_forest_classifier.py
```

This script does the following:
- First, it reads every `.pcap` / `.pcapng` file in the specified directory (and subdirectories) with scapy and extracts TCP and UDP packets. These are grouped into bidirectional flows, with the side opening the connection being the `forward` direction.
- Flows with fewer than 20 packets are discarded, to avoid background noise decreasing the models accuracy (DNS lookups and so on)
- Afterwards, the parser computes 19 features per flow, among them the number of packets, bytes transferred, packet sizes, flow duration and inter-arrivial times and bursts.
- Then 80% of the captures are used for training the model and the other 20% for validation. By using a `GroupShuffleSplit` we make sure to only use 80% of FILES for training and not use some flows of the same file for training and validation.
- Then the script applies a `StandardScaler` and starts the training process.
- After finishing training, the model is evaluated on the remaining 20% of the dataset. After evaluation, it prints accuracy, a classification report, the confusion matrix and feature importances.
- To be able to reuse the model quickly, without training it every time, the script saves the models weights, the scaler and the feature names.

## Classifying additional captures

To classify a new, unseen capture, set the `test_file` path in `predictor.py` and run:

```bash
python predictor.py
```

This script uses the trained, saved model to evaluate and classify this new capture.

- Therefore it first loads the saved model `rf_model.joblib`, `scaler.joblib`, and `feature_names.joblib`, so features are named and scaled exactly as during testing.

- Similar to the training script, the capture is parsed, and its features extracted. 
- Then the script classifies each flow and prints per-flow predictions
- Finally the flow predictions are combined into one prediction for the whole capture, with that prediction being the label most of the flows have been classified with. This is used, because many activities like browsing have streaming-like side-channels, for example loading a large ad while visiting a website. By only predicting the mostly predicted label, these other connections are filtered out. 

## Limitations
This filtering process is vulnerable to many concurrent small connections while doing the specified activity. For example, if the network traffic capture is supposed to capture streaming, but there are 5 or more smaller connection loading ads or cookie banners, these 5 connections may be labeled as browsing. This will cause the whole file to be labeled as browsing, because only the one flow that captures all the actual video streaming traffic will be labeled as streaming, rendering the vote 1:5 for browsing.


## ODENet: build, train and test

### Requirements

- Python **3.11 – 3.13**. Very recent Python releases may not have PyTorch wheels yet; in that case `pip` fails with `No matching distribution found for torch`.
- `requirements.txt` must include `torch`, `numpy` and `scapy` (scapy is used to read PCAP files).

### Dataset layout

Put the captures in one folder per class:

```
dataset/
├── BROWSING/        *.pcap
├── CHAT/            *.pcap
├── FILE_TRANSFER/   *.pcap
└── STREAMING/       *.pcap
```

The folder name is the class label.

### 1. Set up the environment

```bash
cd ODENet
python3 -m venv .venv
.venv/bin/python3 -m pip install -r requirements.txt
```

### 2. Convert the PCAP files to CSV

```bash
.venv/bin/python3 pcap_to_csv.py ../dataset/CHAT --name my_chat
.venv/bin/python3 pcap_to_csv.py ../dataset/STREAMING --name my_streaming
.venv/bin/python3 pcap_to_csv.py ../dataset/BROWSING --name my_browsing
.venv/bin/python3 pcap_to_csv.py ../dataset/FILE_TRANSFER --name my_filetransfer
```

Each CSV row is one unidirectional flow (5-tuple). The files are written to `classes_csvs/<class>/reg/<name>.raw.csv`.

- Flows shorter than 20 packets are discarded (`--min-packets`).
- An existing CSV is not overwritten unless you pass `--force`.

### 3. Train the model

```bash
.venv/bin/python3 train.py
```

`train.py` loads every `classes_csvs/*/reg/my_*.raw.csv`, splits the flows 80/20 (train/test), balances the training set and trains for 100 epochs. At the end it prints the macro-F1 and the confusion matrix.

The best checkpoint is saved as `best_<model>_n<n>.pt` (e.g. `best_ode_n20.pt` for the default ODE-LSTM). The model is selected with `model_name` in `main()`: `ode`, `lstm_size` or `lstm_both`.

Training results:

![Alt text](images/odenet-result.png?raw=true "ODENet training results")

### 4. Classify an external capture

```bash
.venv/bin/python3 predict.py capture.pcap --ckpt best_ode_n20.pt --classes BROWSING,CHAT,FILE_TRANSFER,STREAMING
```

The script prints the longest flows with their predicted class and confidence, and a summary with the share of traffic per class.

- `--classes` must follow the training order. It can be omitted if the checkpoint already stores the class names.
- `--n` must match the value used in training (default 20).
- A `.csv` file in the same format as the training CSVs is also accepted as input.
